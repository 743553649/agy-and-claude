P1 · 设置页语言切换：三个方案对比

AntiGem（com.termux）汉化分支 · feat/zh-cn-i18n · 供拍板用，结论先行

结论：三个方案里只有 C（只做 Android 13+ 的框架 LocaleManager）能同时满足 「零新增依赖 + 不动 AndroidManifest + 不动主题 + 通知/Toast 也跟着变」。

A（加 appcompat）能力最完整，但必须把全应用主题从框架 Material 换成 AppCompat 主题， 所有界面都要视觉回归；B（零依赖 attachBaseContext）在「不能改 AndroidManifest」的约束下是 半成品：界面会变中文，但通知与 Toast 仍是系统语言。

1. 方案 A：加 androidx.appcompat + AppCompatDelegate.setApplicationLocales

A · 官方推荐路径 要加依赖要换主题

改动面：4 处

  • app/build.gradle.kts：加 implementation("androidx.appcompat:appcompat:1.6.1")
  • res/values/themes.xml：把 parent 换成 Theme.AppCompat.Light.NoActionBar（或引入 Material3 的 AppCompat 桥接主题）
  • 需要跟随语言的 Activity 改继承 AppCompatActivity（Compose 内容不变）
  • 设置页加语言项；切换时调 setApplicationLocales(LocaleListCompat.forLanguageTags("zh-CN"))

得到什么：API 24–32 也能真正切换（appcompat 自己包 context）；官方维护，长期稳。

代价与风险：

  • 主题改造是最大风险：全应用从框架 android:Theme.Material 换成 AppCompat 主题， 每个界面的控件默认样式、状态栏、对话框都要重新过一遍
  • appcompat 的「自动保存语言」（autoStoreLocales）要求 manifest 里声明 AppLocalesMetadataHolderService 组件 —— 当前 manifest 没有， 在不改 manifest 的约束下用不了，得自己用 SharedPreferences 存并在启动时回设
  • 新增依赖会改变 R8 输入与 APK 体积（可接受，但要重跑一次真机功能回归）
本机证据：gradle 缓存里的 appcompat-1.6.1.aar 反编译可见 public static void setApplicationLocales(androidx.core.os.LocaleListCompat)； 同时可见运行时校验文案 You need to use a Theme.AppCompat theme (or descendant) with this activity. —— 主题不改就会直接崩。

2. 方案 B：零依赖，自己 attachBaseContext

B · 不加依赖 不动 manifest通知/Toast 不跟随

改动面：5 个 Activity 都要覆写 attachBaseContext(newBase)（或抽一个基类）， 用 createConfigurationContext(config) 把 locale 包进去；切换后 Locale.setDefault() + recreate()；语言偏好自己存 SharedPreferences。

得到什么：不加依赖、不动主题、不动 manifest，界面文案确实能切。

当前约束下的硬伤：

  • 通知与 Toast 不会跟随：P3.7 那批 77 处通知文案走的是 appContext.getString， appContext 来自 applicationContext，它的资源由 Application 决定； 要让 Application 也跟随，必须写自定义 Application 并在 manifest 挂 android:name —— 这正是当前硬约束禁止的
  • 结果会是「界面中文、通知/Toast 英文」的混搭，比不做更容易被当成 bug
  • AiLanguage 依赖 Locale.getDefault()，必须额外显式 Locale.setDefault()，否则 AI 仍回英文
  • 5 个 Activity 各自维护，容易漏（浮窗、文件打开、空间管理这几个冷门入口最容易被漏掉）

什么时候才值得选：如果后续允许加自定义 Application（即允许改 AndroidManifest）， B 会变成「零依赖且通知也跟随」的最优解。

3. 方案 C：只做 Android 13+（框架 LocaleManager + 已声明的 localeConfig）

C · 零依赖、零主题风险、系统级生效 推荐先做仅 Android 13+

改动面：1 个文件（设置页加入口 + 调 API），locales_config.xml 和 manifest 都已经就绪，不用动。

做法：设置页加一项「界面语言 / Language」，选项为「跟随系统 / 简体中文 / English」： 点选时判断 Build.VERSION.SDK_INT >= 33， 调 getSystemService(LocaleManager::class.java).applicationLocales = LocaleList.forLanguageTags("zh-CN")； 32 及以下把该项置灰并提示「系统版本较低，语言跟随系统」。

得到什么：

  • 系统负责重建 Activity 与资源，通知、Toast、AI 注入全部一起跟随（因为 Application 资源也变了）
  • 零新增依赖、不动主题、不动 manifest、可随时回滚（删一个入口即可）
  • 和已有的 android:localeConfig 天然配套

代价与未验证点：

  • 只覆盖 Android 13+；24–32 上该入口只能置灰
  • 本项目 targetSdk = 28：系统的「应用 → 语言」入口一般要求 targetSdk 33+ 才出现， 自定义入口里直接调 API 是否同样生效，必须真机验证（这是选 C 之前唯一的技术悬念）
本机证据：android-33/android-34 的 android.jar 里确有 android.app.LocaleManager，方法为 setApplicationLocales(android.os.LocaleList) / getApplicationLocales()； manifest 已声明 android:localeConfig，res/xml/locales_config.xml 含 en + zh-CN。

6. 无论选哪个，都必须真机验证

  • 待验证C 的 targetSdk 28 悬念：API 33+ 上直接调 LocaleManager 是否真的生效（若无效，C 要降级为「引导用户去系统设置」）
  • 切换后 Locale.getDefault().language 是否变成 zh（决定 AI 是否回中文）
  • 通知与 Toast 文案是否同步变中文（P3 / P3.7 那 228 处 getString）
  • 已存在的通知渠道名不会改名（渠道只在首次创建时写入），需要清数据或重装才能看到新名字
  • release 包（R8 压缩）下同样正常
  • 设置页入口在中文界面下自己也要显示中文（不能出现「界面语言」变成英文的尴尬）

7. 建议的落地顺序

  1. 先做 C：风险最低、可回滚，先把「能切」这件事交付；顺带用真机把 targetSdk 28 的悬念验证掉
  2. 若实测 C 在 13+ 不生效 → 改用 A，但要同时接受「加依赖 + 主题改造 + 全界面视觉回归」， 并为此单独排一批（不建议和文案批次混在一起）
  3. B 不建议，除非未来放开「允许自定义 Application」—— 那时 B 会反超 A
